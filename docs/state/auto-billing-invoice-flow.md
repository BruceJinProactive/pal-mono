# Auto-Billing Invoice Flow

> **Last updated:** 2026-05-27
> **Status:** Current implementation reference

## Purpose

This document explains the automatic billing invoice flow step by step. It
consolidates the current Stripe subscription invoice behavior, arrears billing
webhook behavior, automated analytics invoice email, and unpaid balance accrual.

The short version: when Stripe creates a subscription invoice, pal-mono keeps the
new invoice in draft state for the current billing period. When the next billing
period starts and Stripe creates the next draft invoice, pal-mono finalizes the
previous period's draft invoice and sends the customer an analytics invoice email
with the Stripe invoice PDF attached.

## Scope

This flow covers subscription invoices generated by Stripe and handled through
the Stripe webhook endpoint. It applies to subscription invoices, not one-off
manual invoices.

Invoice-based subscriptions are created with Stripe `collection_method` set to
`send_invoice`, but the webhook flow currently handles any Stripe subscription
invoice that reaches `invoice.created`.

## Step-by-Step Flow

### 1. Subscription is prepared

An admin creates an account subscription in pal-mono. The subscription starts in
`pending` status while project-level billing artifacts are prepared.

For each project on the subscription, pal-mono creates or stores Stripe billing
artifacts such as:

- Project-specific Stripe products
- Base fee prices
- Metered call prices
- Metered order prices
- Billing meters for usage aggregation

These project prices become the Stripe subscription line items.

### 2. Subscription is activated for invoice billing

For no-payment-method or credit-funded customers, the admin activates the pending
subscription through:

```text
POST /v1/admin/accounts/{account_name}/subscriptions/{external_id}/activate
```

The service function is:

```text
activate_subscription_without_payment_method()
```

It performs the following work:

1. Loads the pending `AccountSubscription`.
2. Verifies the account has a Stripe customer ID.
3. Loads linked `ProjectSubscription` rows and collects their Stripe price IDs.
4. Creates the Stripe subscription directly through `stripe.Subscription.create`.
5. Uses `collection_method="send_invoice"`.
6. Uses `days_until_due=30`.
7. Allows hosted invoice payment by card or US bank account.
8. Adds metadata with `subscription_external_id` and `account_id`.
9. Optionally grants account credit when requested by the admin.
10. Updates pal-mono records with the Stripe subscription ID.
11. Sets the account subscription payment method to `invoice`.
12. Sets the subscription status to `active`, or `trialing` when `start_date` is in the future.

The lower-level Stripe helper is:

```text
create_subscription_direct()
```

It uses the subscription external ID as the Stripe idempotency key so retries do
not create duplicate Stripe subscriptions.

### 3. Stripe creates a draft invoice

When Stripe creates a subscription invoice, it sends:

```text
invoice.created
```

The webhook handler is:

```text
_handle_invoice_created()
```

The handler first skips non-subscription invoices. For subscription invoices, it
requires:

- Stripe invoice ID
- Stripe customer ID
- Stripe subscription ID

Then it immediately sets:

```text
auto_advance=False
```

on the new invoice.

This is the core arrears-billing behavior. The invoice stays in draft state for
the billing period so Stripe can continue attaching subscription items and
metered usage before the invoice is finalized.

If pal-mono cannot set `auto_advance=False`, the handler raises the Stripe error
so Stripe retries the webhook. This is intentional: if the invoice auto-finalized
too early, the arrears invoice would be wrong.

### 4. The current period accumulates usage

During the billing period, usage is tracked through Stripe billing meters.

Typical usage inputs include:

- Call meter events
- Order meter events
- Base subscription fees already present as subscription items

Because the invoice is still a draft, the final invoice can include the completed
period's flat fees and metered usage.

### 5. The next invoice triggers finalization of the previous invoice

At the start of the next billing period, Stripe creates a new draft invoice and
sends another `invoice.created` webhook.

The same handler does two things:

1. Keeps the new invoice in draft state with `auto_advance=False`.
2. Finalizes the previous period's draft invoice.

The finalization helper is:

```text
_finalize_previous_draft_invoice()
```

It lists draft invoices for the same customer and subscription, skips the newly
created invoice, and finalizes the older draft invoice or invoices.

In the normal case there is one older draft invoice: the invoice for the billing
period that just ended.

### 6. The automated analytics invoice email is sent

After finalizing the previous draft invoice, pal-mono calls:

```text
send_automated_invoice_email()
```

This function:

1. Retrieves the finalized invoice from Stripe.
2. Reads the invoice billing period from `period_start` and `period_end`.
3. Looks up the pal-mono account by Stripe customer ID.
4. Uses the account `notification_email` as the recipient.
5. Queries internal analytics for the invoice period.
6. Excludes eval calls and configured test phone numbers.
7. Calculates invoice-email metrics.
8. Selects the correct Postmark template.
9. Fetches the finalized Stripe invoice PDF.
10. Sends a Postmark email with the PDF attached.

Metrics included in the email model:

- Calls handled
- Total call minutes
- Estimated staff hours saved
- Total paid orders
- Paid order dollar value
- Total reservations
- Billing period
- Palona tax ID

Template selection:


| Activity                | Template variant       | Template ID |
| ----------------------- | ---------------------- | ----------- |
| Calls only              | `answering`            | `42569088`  |
| Orders                  | `ordering`             | `44949422`  |
| Reservations            | `reservation`          | `44949423`  |
| Orders and reservations | `ordering_reservation` | `44949424`  |


If required data is missing, the automated email is skipped rather than failing
the webhook. Examples:

- Stripe invoice has no period dates
- No pal-mono account matches the Stripe customer
- Account has no `notification_email`
- Stripe invoice PDF cannot be fetched

### 7. Stripe applies credits or waits for payment

Stripe applies any customer credit balance to the finalized invoice. If credits
fully cover the invoice, Stripe can mark it paid with no remaining amount due.

For invoice-based subscriptions, remaining balances are payable through Stripe
invoice payment methods such as card or US bank account. Stripe owns the hosted
invoice and payment collection mechanics.

The pal-mono automated analytics email attaches the invoice PDF. The
`invoice.finalized` webhook payload also includes Stripe invoice URLs such as
`hosted_invoice_url` and `invoice_pdf` for downstream notification handling.

Current implementation note: `_finalize_previous_draft_invoice()` finalizes the
Stripe invoice and then sends the Postmark analytics email. It does not call
`stripe.Invoice.send_invoice()`. If the hosted payment link must appear in the
customer-facing analytics email, confirm the Postmark template payload includes
it or extend `send_automated_invoice_email()` to pass `hosted_invoice_url`.

### 8. Payment webhooks send billing notifications

Stripe payment outcomes are handled separately:


| Stripe event                | Handler behavior                         |
| --------------------------- | ---------------------------------------- |
| `invoice.payment_succeeded` | Sends a payment succeeded billing event  |
| `invoice.payment_failed`    | Sends a payment failed billing event     |
| `invoice.finalized`         | Sends an invoice finalized billing event |
| `invoice.upcoming`          | Sends an upcoming invoice billing event  |


These billing events go through `services.notification_service`.

Payment notification failures are logged and do not block webhook processing.

### 9. Past-due invoices accrue onto the next draft invoice

After preparing the new draft invoice and finalizing previous drafts, the
`invoice.created` handler checks for unpaid invoices that should roll forward.

It lists open invoices for the same customer and subscription, then filters to
invoices that:

- Are not the current invoice
- Have a `due_date`
- Are past due
- Have `amount_remaining > 0`

If there is no past-due balance, the handler logs a no-op.

If a past-due balance exists, pal-mono:

1. Sums the remaining amounts.
2. Adds a line item to the new draft invoice.
3. Uses a description like `Prior unpaid balance (N invoice(s))`.
4. Uses an idempotency key based on the new invoice and old invoice IDs.
5. Voids the old unpaid invoices to prevent double billing.
6. Logs any partial void failure for manual review.

This makes the new invoice the consolidated bill for current charges plus prior
unpaid balance.

### 10. Subscription deletion finalizes remaining drafts

When Stripe sends:

```text
customer.subscription.deleted
```

pal-mono finalizes any remaining draft invoices for that subscription before
marking the subscription cancelled locally.

This prevents the final billing period's draft charges from being stranded.

## Manual Admin Paths

The automatic flow above is separate from the admin/manual invoice email flow.

The manual support path is:

1. Admin calls the billing metrics endpoint:
  ```text
   GET /v1/admin/accounts/{account_name}/billing/metrics?start_date=...&end_date=...
  ```
2. The manage app can prefill invoice email fields from real usage metrics.
3. Admin sends an invoice email through the account or project invoice email endpoint.
4. The request can provide a `stripe_invoice_id`, letting pal-mono fetch the PDF from Stripe.

This is useful for manual follow-up, corrections, or one-off customer support,
but it is not the normal automatic monthly invoice path.

## Operational Requirements

Stripe webhook events required for the full flow:

- `invoice.created`
- `invoice.finalized`
- `invoice.payment_succeeded`
- `invoice.payment_failed`
- `invoice.upcoming`
- `customer.subscription.created`
- `customer.subscription.updated`
- `customer.subscription.deleted`
- `customer.subscription.trial_will_end`

Environment and configuration requirements:

- `STRIPE_API_KEY` configured for Stripe API calls
- `STRIPE_WEBHOOK_SECRET` configured for webhook signature verification
- Account has `stripe_customer_id`
- Account has `notification_email` for automated invoice email delivery
- Stripe customer balance is used for credits
- Stripe dunning settings should not cancel invoice-based subscriptions automatically

## Failure Behavior


| Failure                                        | Behavior                                      |
| ---------------------------------------------- | --------------------------------------------- |
| Cannot set `auto_advance=False` on new invoice | Raise so Stripe retries the webhook           |
| Cannot list draft invoices for finalization    | Log and continue                              |
| Cannot finalize an older draft invoice         | Log and continue with other drafts            |
| Automated email data missing                   | Skip email and log                            |
| Cannot fetch invoice PDF                       | Skip email and log                            |
| Cannot list open invoices for accrual          | Log and continue without accrual              |
| Cannot add accrued balance line item           | Log and continue without voiding old invoices |
| Some old invoices cannot be voided             | Log warning for manual review                 |


## Mental Model

Think of the system as a rolling draft:

```text
Billing period A starts
  -> Stripe creates draft invoice A
  -> pal-mono freezes invoice A as draft
  -> usage accrues into invoice A

Billing period B starts
  -> Stripe creates draft invoice B
  -> pal-mono freezes invoice B as draft
  -> pal-mono finalizes invoice A
  -> pal-mono emails invoice A with analytics and PDF
  -> unpaid older invoices, if any, roll into invoice B
```

The customer receives the finalized invoice after the period is complete, not at
the beginning of the period.
