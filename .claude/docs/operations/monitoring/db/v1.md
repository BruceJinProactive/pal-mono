# Monitoring System - Database Schema V1

## Overview

This document defines the actual database schema for the monitoring system, serving as the source of truth for implementation.

**Architecture**: Multi-tenant with project-level isolation
**Purpose**: Continuous monitoring of store operations through automated analysis
**Data Retention**: 90 days for runs (configurable)

---

## Table 1: monitoring_configs

**Purpose**: Define what to monitor, when to run checks, and how to alert

### Schema

| **Column Name**    | **Data Type**  | **Nullable** | **Default**   | **Indexed** | **Description**                                           |
| ------------------ | -------------- | ------------ | ------------- | ----------- | --------------------------------------------------------- |
| **`id`**           | `UUID`         | No           | `uuid4()`     | Yes (PK)    | **Primary Key** - Unique monitoring configuration ID      |
| `project_id`       | `UUID`         | No           | -             | No          | References `projects.id` (no FK constraint)               |
| `signal_source_id` | `UUID`         | No           | -             | No          | References `signal_sources.id` (no FK constraint)         |
| `name`             | `VARCHAR(255)` | No           | -             | No          | Human-readable name (e.g., "Counter Cleanliness Monitor") |
| `description`      | `VARCHAR`      | Yes          | `NULL`        | No          | Optional context and details about the monitor            |
| **`rules`**        | `JSONB`        | No           | `'{}'::jsonb` | No          | **The Logic** - AI prompts or numeric thresholds          |
| `enabled`          | `BOOLEAN`      | No           | `true`        | No          | Main on/off switch for this monitor                       |
| `created_at`       | `DATETIME(TZ)` | No           | `now()`       | No          | Record creation timestamp                                 |
| `updated_at`       | `DATETIME(TZ)` | Yes          | `now()`       | No          | Last modification timestamp (auto-updated on change)      |

### Business Rules

✅ **Uniqueness**: Name must be unique per project
✅ **Enabled**: Main on/off switch controls whether monitoring is active
⛔ **Deletion**: Cannot delete if dependent runs exist

### Rules Column Structure (JSONB)

The `rules` column defines the monitoring logic. Two main types:

#### AI Analysis Example

```json
{
  "type": "ai_analysis",
  "prompt": "Check if counter is clean and organized",
  "reference_image_urls": [
    "s3://bucket/reference1.jpg",
    "s3://bucket/reference2.jpg"
  ],
  "comparison_mode": "best_match",
  "confidence_threshold": 0.8
}
```

#### Threshold Check Example

```json
{
  "type": "threshold",
  "metric": "temperature",
  "operator": "between",
  "min": 35,
  "max": 40,
  "unit": "fahrenheit"
}
```

## Table 2: monitoring_runs

**Purpose**: Complete execution history of every monitoring check

### Schema

| **Column Name**            | **Data Type**  | **Nullable** | **Default**   | **Indexed** | **Description**                                       |
| -------------------------- | -------------- | ------------ | ------------- | ----------- | ----------------------------------------------------- |
| **`id`**                   | `UUID`         | No           | `uuid4()`     | Yes (PK)    | **Primary Key** - Unique run execution ID             |
| **`monitoring_config_id`** | `UUID`         | No           | -             | No          | References `monitoring_configs.id` (no FK constraint) |
| `trigger_metadata`         | `JSONB`        | No           | `'{}'::jsonb` | No          | Payload that triggered it (e.g., S3 event details)    |
| `started_at`               | `DATETIME(TZ)` | No           | -             | No          | Actual execution start time                           |
| `completed_at`             | `DATETIME(TZ)` | Yes          | `NULL`        | No          | Actual execution completion time                      |
| **`evaluation_result`**    | `JSONB`        | No           | `'{}'::jsonb` | No          | **Analysis** - AI's JSON output or threshold check    |
| `error_message`            | `TEXT`         | Yes          | `NULL`        | No          | Human-readable error if execution failed              |

### Business Rules

📝 **Immutability**: Runs are write-once, never updated after completion
🗑️ **Retention**: Auto-deleted after 90 days (configurable)
📸 **Images**: Stored in S3, URLs referenced in `trigger_metadata` or `evaluation_result`

### Key Design Patterns

**🔒 Multi-Tenant Isolation**

- All queries filter by `project_id`
- `monitoring_configs.project_id` references `projects.id` (1:1 relationship)
- `monitoring_configs.signal_source_id` references `signal_sources.id` (1:1 relationship)
- `monitoring_runs.monitoring_config_id` references `monitoring_configs.id` (1:N relationship)

**⚡ No Foreign Key Constraints**

- All UUID references are logical relationships without DB-enforced FK constraints
- Referential integrity managed in application layer for flexibility
- Allows for soft deletes and historical data retention

**📋 JSONB for Flexibility**

- `rules`: Supports multiple monitoring types without schema changes
- `trigger_metadata`: Captures diverse trigger contexts
- `evaluation_result`: Stores varied analysis outputs
